## 2. What the code needs (read from `session.py`, `session_init.py`, `realkit.py`)

* The "full" mode builds `lowerdir=<template>:/` and pivots into it (`session_init.py` ~36-67). Everything the session runs AFTER the pivot comes from that tree: `dbus-daemon`, `at-spi-bus-launcher`, `openbox` and the server's python (`start_real_desktop`). Xvfb is a HOST process and needs nothing from the image.
* The kit's venv is built on `/usr/bin/python3.12` with system site-packages (`realkit.py`: `NEEDED_FILES`, `build`); a 22.04 image has python 3.10, so the kit as built cannot run inside an image root.
* CRIU restore assumes `/` as a lower layer (`session.py` restore path, ~385). An alternative base root is therefore for cold-reset stages only.
* What a session actually STARTS after the pivot, read from `session_init.start_real_desktop` (`rootcheck.desktop_programs`, not guessed): `dbus-daemon`, `/usr/libexec/at-spi-bus-launcher` and `openbox`, then the pinned server on the kit's python. `xclip` and `wmctrl` are NOT launched there; the pinned server runs `wmctrl` (and others, derived from its source with `rootcheck.server_programs`) per task.
* **Whether GNOME Shell can run inside a session is unvalidated**, and is not concluded from package names: a session has its own init, with no logind or system D-Bus (an `exec_systemd` experiment exists in `session.py`; it has host side effects, is unvalidated and is NOT used). The root/home plumbing does NOT declare GNOME or the user identity matched.

## 3. The decision: route B first, route A kept as the fallback, both unvalidated

* **Route A, install the VM's userland on a 22.04 Drums host.** Needs a 22.04 host (the kit, CRIU, cgroup and nested-virtualization findings so far are for 24.04), GNOME 42, `google-chrome-stable` 130.0.6723.58 (Google's apt repository serves the CURRENT stable, so an old `.deb` must be fetchable from a pool URL: availability UNVERIFIED), and LibreOffice 7.3.7 from the jammy archive. **It cannot reach per-package equality**: Ubuntu supersedes versions, and old ones may no longer be installable. Kernel still differs.
* **Route B, use the image's own root filesystem, mounted READ-ONLY, as the base layer.** Same bytes: every package and version, Chrome 130 and LibreOffice 7.3.7 with no download (the old-Chrome problem disappears), `/home/user` and its contents. Kernel still differs. Needs: the read-only mount, the base-root parameter, a python that runs the pinned server inside the image root, and possibly a window manager (below). **Recommended as the first thing to validate** because it is the only route that can give package-level identity, and it costs one host session to find out whether it works.
* Neither route changes the uid, ownership, network or privileges: sessions keep running as ROOT with a different HOME, and the veth network stays. The VM user `user` with sudo is a recorded difference, and changing it would be a separate, explicit decision.
* **Correction from the real image manifest (1932 packages).** wmctrl 1.07-7build1 is PRESENT; openbox and xclip are ABSENT; there is no package named `mutter`, but `gir1.2-mutter-10`, `libmutter-10-0`, `mutter-common` 42.9-0ubuntu4 and `gnome-shell` 42.9-0ubuntu2 are present; Chrome 130.0.6723.58-1; LibreOffice 1:7.3.7-0ubuntu0.22.04.4; Python 3.10.6-1~22.04. The Drums manifest tracks only 10 packages, 7 common with the VM and all 7 at different versions: that is NOT a full inventory comparison (the report now says so and gives no fraction).

## 14. First actual GNOME attempt (source c5ca1a3): reached boot, GNOME Shell exited; private system bus added

Owner-reported: `rootcheck` passed on the real image; the boot reached the desktop stage: exact Xvfb started, the OSWorld server ran as uid 1000 under Python 3.10 with all imports returning 0, and the screenshot was a PNG. GNOME Shell 42.9 / mutter 42.9 started (PIDs 66 then 122) and both exited with code 1; the screenshot showed GNOME's "Oh no! Something has gone wrong" screen. Stderr: `Gio.IOErrorEnum: Could not connect: No such file or directory` from `Gio.js` (`get_system`) via `status/power.js` → `AggregateMenu._initializeUI`; gnome-session respawned too fast; `gsd-*` reported the system bus unavailable. Cause read from the log: no system D-Bus socket inside the session. Minimal fix, offline and untested live: `Supervisor(system_bus=True)` (`--system-bus`, default off, boot_validate on) starts a PRIVATE `dbus-daemon --system` inside the session's own mount namespace before the session bus and the desktop (its `/run` is the session's private tmpfs, so the socket exists only there; the host's system bus and logind are never bound in). Why this and nothing else, in sequence: (1) system bus: `power.js`/`gsd-*` connect to it at start; (2) logind: gnome-shell 42's login manager falls back to a dummy when `/run/systemd/seats` is absent, which is the case in the private `/run`, so no logind is started; (3) upower, accountsservice and polkit are NOT started: clients get a D-Bus "service unknown" instead of a missing socket (not tested; if GNOME still fails on them, the next smallest step is decided from the logs, not assumed). **Parity impact:** the session now runs a private system bus the incumbent VM has as part of systemd's full stack, while logind/upower/accounts/polkit are absent here; that is a structural difference and no matched-desktop claim is made unless the live run shows the same shell identity.

`boot_validate` fixes: the import check no longer demands the exact whole output (Xlib xauth warnings were rejected); it parses a `DRUMS_JSON:` sentinel line, keeps the raw output, and still fails on a non-zero return code or a missing sentinel. Desktop logs are now saved with their head AND tail.

## 15. Corrections to the private system bus (review of 82af27a; not yet executed live)

Two gaps found in review and closed in code. (1) `system_bus=True` is now refused unless `root_mode="full"` AND `netns=True` (checked in the Supervisor before any effect, and again in the init); in `home` mode `/run` is the HOST's, where the daemon would have touched the host's socket directory. The init also checks, before starting anything, that `/run` is a tmpfs mount of its own mount namespace and that no bus socket exists there yet, and it drops an inherited `DBUS_SYSTEM_BUS_ADDRESS` first. (2) A stock `dbus-daemon --system` loads `<standard_system_servicedirs/>` and the service launch helper and could therefore ACTIVATE upower/accounts/polkit/logind services (the documented mechanism: system services launched by the daemon itself or through systemd). The earlier text saying none are started was therefore not justified. The explicit policy is now NO activation: the daemon runs from a generated copy of the image's own `system.conf` with the service directories and the launch helper removed (the private copy lives in the session's tmpfs `/run`, and its hash is recorded); the image's policy files are kept. The identity mark records the socket inode, the mount-namespace id, the configuration hash, the activation policy and any process found under the bus (expected: none). Whether GNOME tolerates a bus with no services is UNKNOWN until a live run; "unknown" is not "matched". Tests cover the refusals, the configuration rewrite, the privacy preconditions and the address handling with fakes; the two-session isolation (distinct sockets and namespaces) follows from each session's own mount namespace and is NOT tested live.

## 16. Real-daemon defects found offline in bcb264c and their fixes

`dbus-daemon --system --config-file=...` is rejected by the real daemon (the two options are mutually exclusive); the command is now `dbus-daemon --config-file=<generated> --fork --print-pid=1 --print-address=1`, where the generated file carries `<type>system</type>`. The earlier regex rewrite was also not fail-closed: an included file could bring `<servicedir>`/`<servicehelper>` back. The generated configuration is now FLATTENED: every `<include>`/`<includedir>` is read from the image and inlined, the service-launching elements and the SELinux/AppArmor hooks are dropped, the only listen address is the private socket, and any element outside a fixed allow-list, any missing non-optional include and any non-busconfig include raises. Kept: the image's authentication, limits and policy rules. Differences from the stock bus (all deliberate): no activation of any kind, no LSM hooks, one listen address. `hashlib`, `glob` and `ElementTree` are imported at module level, so they are loaded before the pivot (a test checks the init-path functions).

New test: two REAL unprivileged `dbus-daemon` processes started with the real command line from generated configs (one deliberately including a service file and an include directory that tries to bring launching back) get different socket paths and different `GetId` values, list no activatable service from the stripped files, do not launch one when it is requested (`ServiceUnknown`), leave the host's own system-bus socket (if any) unchanged, and are killed afterwards.
